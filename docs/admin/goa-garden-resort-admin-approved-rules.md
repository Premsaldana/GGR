# Approved Admin Workflow and Security Rules

## Goa Garden Resort Admin System

## 1. Authoritative user journey

The approved end-to-end journey is:

```
Sign in → Dashboard → Calendar → Empty date → Guest form → Bill & UPI QR generation (shareable) → Payment status → Invoice PDF generation
```

The admin must first create or save the reservation details. The system then displays the calculated bill and opens an explicit **Set payment amount** step. The admin enters or selects the amount to request, reviews it, and generates a shareable bill/QR artifact. Payment status remains separate and must be updated manually until a verified payment integration exists. The final invoice PDF is generated from the saved invoice version and includes the same approved billing data.

## 2. Authentication rule

Only the exact email address `goagardenresort@gmail.com` is authorized to access the admin application. Authentication must use two-step authentication. The first factor must verify ownership of this email address, preferably through a one-time email code or magic link. The second factor must be a time-based one-time password (TOTP) generated by an authenticator app such as Google Authenticator, Microsoft Authenticator, or 1Password, or an equivalent provider-supported MFA flow that provides the same two-step security. This is now the approved factor combination; the implementation must not downgrade it to email-only or password-only access.

The email address must be enforced on the server through an allowlist or owner-admin mapping. Hiding the route or checking the email only in the frontend is insufficient. No shared default password, hard-coded password, or credential should be placed in source control. The system must support logout, session expiry, failed-attempt handling, rate limiting, and recovery by the owner.

Because only one email is currently approved, the first release can implement a single `owner_admin` identity. The data model should still support future role-based accounts without granting them access now.

## 3. Admin-selected QR amount

The QR amount is not automatically assumed to be the invoice total, balance, security deposit, or advance. After the guest form is completed and the bill is calculated, the admin must explicitly set the payment amount.

The amount-setting step should show:

| Field | Behavior |
| --- | --- |
| Calculated total invoice amount | Read-only reference |
| Advance already received | Read-only reference |
| Calculated balance due | Read-only reference |
| Refundable security deposit | Read-only reference |
| Payment amount for this QR | Admin-entered or selected amount; required |
| Payment note/reference | Defaults to invoice number and reservation reference; editable within a safe length |
| Payment method | UPI QR initially; future methods can be added |

The server must validate that the selected amount is a non-negative INR amount and must store exactly what the admin approved. The QR screen must display the same amount that is encoded. Any later change to the invoice or selected amount must invalidate the previous QR artifact or create a new version.

## 4. Shareable bill and QR artifact

“Shareable” means the admin can generate a controlled link or downloadable artifact that can be sent to the guest. The first safe implementation should use a signed, expiring, read-only share token that reveals only the invoice and payment-request information needed by the guest. The token must not expose the admin dashboard, edit controls, audit history, unrelated guest records, or authentication data.

The share view should show the resort identity, guest-facing reservation reference, stay summary, invoice amount, selected payment amount, UPI ID, QR image, payment instructions, and a clear message that payment is pending until staff verifies it. The admin must be able to revoke or regenerate a share link. Share links should expire by configurable policy and should not be indexed by search engines.

If implementation scope must remain smaller, the fallback is a downloadable invoice PDF containing the QR and a copyable UPI payment URI. The product requirements should still reserve the signed-link model for the next iteration.

## 5. Payment status

The system must distinguish payment request from payment receipt. Initial payment statuses are `not_requested`, `qr_generated`, `pending_verification`, `partially_paid`, `paid`, `rejected`, and `refunded` if approved. Generating, downloading, opening, or scanning the QR must never change the status to `paid`.

An authorized admin must manually record a payment with amount, mode, date/time, reference, note, and actor. The system must append an audit event. A future payment gateway or bank-confirmation integration may update status only through a verified server-side mechanism.

## 6. Invoice PDF

Invoice PDF generation is a first-release requirement. The PDF must be generated from the stored invoice version after the bill and selected QR amount are saved. It must preserve the supplied Goa Garden Resort template structure and contain reservation details, line items, totals, payment summary, amount in words, policies, signature areas, and the selected QR/payment instructions when enabled.

The PDF should be downloadable from the reservation detail, invoice preview, and shareable bill flow. It should use a stable filename such as `GGR-{invoiceNumber}-{guestSlug}.pdf`. Issued invoice versions must be reproducible; editing a reservation after issue must create a new revision or require explicit reissue.

## 7. Approval status

These rules supersede earlier assumptions that the QR amount would default to the total or balance. The authentication decision is finalized: verify `goagardenresort@gmail.com` by email and require a TOTP/authenticator-app code, or use an equivalent provider-supported MFA flow with the same security properties. The owner’s approval is recorded; Antigravity may implement this requirement in the authentication slice.
